Backend экспериментального стенда KomusModelLab
1. Назначение

Backend предназначен для проведения воспроизводимых экспериментов по прогнозированию дефолта контрагента.

Он отвечает за полный цикл одного эксперимента:

Данные
   ↓
Выбор набора признаков
   ↓
TRAIN / TEST
   ↓
Создание модели
   ↓
Обучение
   ↓
Предсказания
   ↓
AUC / GINI / Recall / F1
   ↓
Сохранение результата

Backend отделён от пользовательского интерфейса Streamlit. Это позволяет запускать эксперименты как из демонстрационного приложения, так и непосредственно из Python-кода.

2. Структура backend
src/
├── check_data.py
├── data_split.py
├── experiment_runner.py
├── feature_sets.py
├── metrics.py
├── models.py
├── run_comparison.py
└── fix_history.py
Основные модули

experiment_runner.py

Основной исполнитель эксперимента.

Отвечает за:

загрузку данных;
выбор признаков;
загрузку фиксированного TRAIN / TEST;
создание модели;
обучение;
получение прогнозов;
расчёт метрик;
измерение времени выполнения;
сохранение результата в историю.

feature_sets.py

Содержит зарегистрированные наборы признаков и функцию получения соответствующего набора.

Кроме заранее определённых наборов backend поддерживает пользовательский список признаков.

models.py

Отвечает за создание выбранной модели и определение правил обработки пропусков.

Используется через интерфейс:

create_model(model_name)

и

get_nan_rule(model_name)

Таким образом, логика конкретных моделей не находится внутри experiment_runner.py.

metrics.py

Содержит расчёт и вывод основных метрик эксперимента:

AUC;
GINI;
Recall;
F1.

data_split.py

Используется для формирования и сохранения фиксированного разбиения данных.

3. Данные

Backend работает с подготовленными parquet-датасетами.

Для базового набора используется:

data/base/komus_base38.parquet

Для набора с дополнительными признаками:

data/features/komus_base38_dynamic9.parquet

Целевая переменная:

DefMark
4. Наборы признаков

Backend поддерживает два уровня выбора признаков.

Предварительно определённый набор

Например:

BASE COMPACT
BASE + SPARK

Набор получается через:

get_feature_set(feature_set_name)
Пользовательский набор

В run_experiment() можно передать конкретный список:

selected_features=[
    "A1_norm",
    "A4_norm",
    "B2_norm",
    "D1_norm",
]

В этом случае эксперимент проводится только на выбранных признаках.

Перед запуском выполняется проверка:

существует ли каждый выбранный признак в текущем наборе;
не передан ли пустой список.

Если обнаружены неизвестные признаки, backend останавливает эксперимент с понятным сообщением об ошибке.

Это позволяет использовать демонстрационное приложение для исследования влияния отдельных признаков и их комбинаций.

5. Фиксированное TRAIN / TEST

Для всех экспериментов используются заранее сохранённые индексы:

experiments/
├── train_indices.csv
└── test_indices.csv

Backend загружает их функцией:

load_split()

и формирует:

X_train
X_test
y_train
y_test

Размеры выборок не меняются между экспериментами.

Это важно для корректного сравнения результатов:

при изменении модели или набора признаков мы сравниваем результаты на одной и той же тестовой выборке.

Таким образом, изменение метрик связано с экспериментируемым фактором, а не с новым случайным разбиением данных.

6. Запуск эксперимента

Основная функция:

run_experiment(
    model_name,
    feature_set_name,
    selected_features=None,
)

Пример запуска:

result = run_experiment(
    model_name="LightGBM",
    feature_set_name="BASE COMPACT",
)

Для пользовательского набора:

result = run_experiment(
    model_name="LightGBM",
    feature_set_name="BASE COMPACT",
    selected_features=[
        "A1_norm",
        "A4_norm",
        "B2_norm",
        "D1_norm",
    ],
)
7. Обучение модели

После формирования TRAIN / TEST backend создаёт выбранную модель:

model = create_model(model_name)

После этого выполняется обучение:

model.fit(X_train, y_train)

Backend не содержит в experiment_runner.py отдельной логики для каждой модели. Создание моделей вынесено в models.py.

Это позволяет добавлять новые модели без изменения основного сценария эксперимента.

8. Обработка пропусков

Перед обучением backend сообщает правило обработки NaN, определённое для выбранной модели:

get_nan_rule(model_name)

При этом сам experiment_runner.py не содержит жёстко заданного универсального способа заполнения пропусков.

Правила находятся на уровне реализации конкретных моделей.

9. Получение прогнозов

После обучения модель получает вероятности дефолта для тестовой выборки:

y_proba = model.predict_proba(X_test)[:, 1]

Именно вероятности используются для расчёта основных метрик качества модели.

10. Метрики

Для каждого эксперимента рассчитываются:

AUC

Площадь под ROC-кривой.

GINI

Используется как основная метрика сравнения моделей:

GINI = 2 × AUC − 1
Recall

Доля правильно обнаруженных дефолтных компаний.

F1

Баланс между Precision и Recall.

Расчёт вынесен в:

src/metrics.py
11. Измерение времени

Для каждого эксперимента измеряется фактическое время выполнения:

perf_counter()

В результат записываются:

время начала;
время окончания;
продолжительность эксперимента.

Это позволяет сравнивать не только качество моделей, но и вычислительную стоимость экспериментов.

12. История экспериментов

Результаты сохраняются в:

experiments/experiment_log.csv

В историю записываются только поля, необходимые текущему интерфейсу:

start_time
model
feature_set
GINI
AUC
Recall
F1
elapsed_seconds

Пример:

2026-08-23 00:14:29,
LightGBM,
BASE COMPACT,
0.789959,
0.894980,
0.352656,
0.472185,
3.88

История используется демонстрационным интерфейсом для отображения выполненных экспериментов.

13. Результат функции

run_experiment() возвращает словарь с полной информацией об эксперименте:

{
    "start_time": ...,
    "end_time": ...,
    "elapsed_seconds": ...,
    "model": ...,
    "feature_set": ...,
    "n_features": ...,
    "train_size": ...,
    "test_size": ...,
    "AUC": ...,
    "GINI": ...,
    "Recall": ...,
    "F1": ...
}

Таким образом, интерфейс не выполняет машинное обучение самостоятельно — он передаёт параметры backend и получает готовый результат.

14. Связь с демонстрационным интерфейсом

Пользовательский интерфейс находится в:

app/app.py

Streamlit-приложение отвечает за:

выбор модели;
выбор набора признаков;
выбор признаков;
отображение процесса выполнения;
вывод метрик;
отображение истории экспериментов.

Backend при этом остаётся независимым от Streamlit.

Схематично:

                 STREAMLIT
                app/app.py
                    │
                    │ параметры
                    ▼

                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
 feature_sets     models       metrics
        │            │            │
        └────────────┼────────────┘
                     ▼
                Результат
                     │
                     ▼
             experiment_log.csv
15. Текущее состояние backend

На текущем этапе реализовано:

загрузка подготовленных данных;
фиксированное TRAIN / TEST;
работа с несколькими наборами признаков;
выбор произвольного поднабора признаков;
проверка выбранных признаков;
создание выбранной модели через единый интерфейс;
обучение модели;
получение вероятностей дефолта;
расчёт AUC, GINI, Recall и F1;
измерение времени выполнения;
сохранение результатов экспериментов;
передача результатов в демонстрационный интерфейс.
Главное расширение последней версии

Ранее backend работал преимущественно с заранее определёнными наборами признаков.

В текущей версии добавлен параметр:

selected_features

Поэтому один и тот же backend теперь позволяет проводить эксперименты вида:

модель
   ×
набор признаков
   ×
конкретный список признаков

Это является основой для следующего этапа исследования — анализа влияния отдельных признаков и их групп на качество модели.

16. Следующий этап

Следующим этапом является развитие демонстрационного интерфейса вокруг уже реализованного backend:

каталог всех доступных признаков;
русские описания признаков;
возможность редактирования описаний;
визуальное разделение используемых, слабых/избыточных и исключённых признаков;
выбор произвольного набора признаков;
запуск эксперимента непосредственно из интерфейса;
сравнение результатов разных наборов признаков.
